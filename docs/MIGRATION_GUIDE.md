# Migration Baseline & Testing — Sprint 1

Status: **schema-side work complete and pre-flight audited by hand; the actual `prisma migrate dev` generation step has not run** — it needs a live Postgres connection and the Prisma query-engine binary, neither of which exist in the environment this was written in (no network, no DB). This document is written to be followed exactly on a machine that has both, per the same standing instruction the rest of this repo's docs follow.

I deliberately did **not** hand-write `migration.sql` myself. Prisma's SQL generation is mechanical but exact — column types, `ON DELETE` behavior on each relation, index naming — and a hand-written guess that's subtly wrong creates schema drift that's harder to debug later than just not having a migration yet. Same principle this codebase already applies to Paystack/Termii: a fake success path is worse than a loud failure. `scripts/verify-migration.sh` below runs the real generation against a real (disposable, dockerized) Postgres — that's the actual baseline, not this document's prose.

## Pre-flight schema audit (done, zero risk, no DB needed)

Checked by hand for the specific things that make `prisma migrate dev` fail or behave unexpectedly:

- **Relation ambiguity** — every model pair with more than one possible relation path is explicitly named (`InquiryBuyer`, `ServiceRequestCustomer`). Every other relation is a single unambiguous path. No ambiguous-relation errors expected.
- **Native array support** — `ProviderProfile.categories ServiceCategory[]` requires the `postgresql` provider specifically (not `mysql`/`sqlite`) — confirmed the datasource block is `postgresql`.
- **BigInt columns** (`priceNaira`, `creditBalanceNaira`, `commissionOwedNaira`, `amountNaira`, offering/request price fields) all map cleanly to Postgres `BIGINT` — no precision concerns Prisma can't express.
- **No explicit `onDelete` on any relation** — this means Prisma's default (`Restrict` for required relations, `SetNull` for optional ones) applies everywhere. Concretely: you cannot delete a `User` who has a `RealtorProfile`/`ProviderProfile`/listings/etc. without deleting those first — the DB will reject it. This matches the existing design decision documented in the schema and Technical Spec ("no soft-delete initially, hard status transitions are sufficient at this scale") — flagging it here so it's a known behavior, not a surprise the first time someone tries to hard-delete a test user.
- **Composite key** (`SavedListing`) and **unique constraint doubling as an index** (`PaymentTransaction.providerRef`) are both standard Prisma patterns, no special handling needed.

Nothing found that should block a clean `migrate dev` run.

## The actual baseline generation (run this — not simulated, not summarized)

```bash
# 1. Bring up a disposable Postgres — same one docker-compose.yml already
#    defines for local dev, nothing new to configure.
docker compose up -d postgres
docker compose exec postgres pg_isready -U ultra   # wait for "accepting connections"

# 2. From a clean checkout with no packages/db/prisma/migrations/ directory,
#    this creates it — the actual clean baseline, generated by Prisma against
#    the real schema, not hand-authored.
DATABASE_URL="postgresql://ultra:ultra_dev_password@localhost:5432/ultra_dev" \
  pnpm --filter @ultra/db exec prisma migrate dev --name init

# 3. Confirm it applied cleanly and matches the schema with nothing pending.
DATABASE_URL="postgresql://ultra:ultra_dev_password@localhost:5432/ultra_dev" \
  pnpm --filter @ultra/db exec prisma migrate status
```

Commit the resulting `packages/db/prisma/migrations/` directory. That directory *is* the migration history — everything downstream (staging, production, every future migration) depends on this first one being right.

## Rollback / recovery procedure

Prisma does not generate automatic "down" migrations — this is a real gap to have an explicit answer for, not an oversight to paper over. Two distinct scenarios, two different answers:

**A migration fails partway through `migrate deploy` in staging/production** (a broken migration file, a constraint violation against existing data): `prisma migrate deploy` runs each migration in its own transaction where the database supports it (Postgres does), so a failed migration rolls back automatically and the database is left in its prior, consistent state. The fix is to correct the migration file and redeploy — not to hand-edit the database, and not to delete/renumber the failed migration file (that breaks the history for every other environment that already saw it).

**A migration succeeded but the resulting schema/behavior is wrong and needs to be undone**: write and apply a new, forward migration that reverses the change (e.g., a migration that drops the column the previous one added), the same way you'd fix any other bug — never edit or delete a migration that's already been applied anywhere. If the bad migration already corrupted data (not just schema), restore from the PITR backup per `docs/OPERATIONS.md`'s backup section instead of trying to hand-repair it — this is exactly the scenario that section's "practice a restore before you need it for real" advice is for.

## Production migration command — confirmed

Already documented in `docs/DEPLOYMENT.md`, restated here since Sprint 1 explicitly asks to confirm it:

```bash
DATABASE_URL="<production-url>" pnpm --filter @ultra/db exec prisma migrate deploy
```

**Never `prisma migrate dev` outside local development** — `migrate dev` can prompt for a destructive reset if it detects drift; `migrate deploy` only ever applies pending migrations and refuses to do anything else. This distinction is the whole reason two separate commands exist.
